# План базового бенчмарка «что происходит без ничего»

## Цель

Снять **честный профиль нетронутого Paper 1.21.8** под большой энтити-нагрузкой:
сколько это стоит в MSPT/TPS/RAM и **какие именно методы JVM жгут время**.
Это данные, на которых строится дизайн c-entities. Никакой оптимизации до
получения этих цифр.

## Где крутится

GitHub Actions (`ubuntu-latest`, 4 vCPU, 16 GB RAM) — workflow `baseline.yml`.
Каждый прогон = отдельный runner, параллельная матрица. Артефакты:
`baseline.json` (сырые замеры), `rec.jfr` (Java Flight Recorder),
`hotspots.md` (top фреймов), `REPORT.md` (итог). Сводный отчёт
коммитится в `reports/baseline/`.

## Методика (важные решения)

1. **Суперплоский мир** (`level-type=minecraft:flat`), view-distance=4,
   structures off, randomTickSpeed=0, doMobSpawning=false, погода ясная —
   чтобы мерить именно энтити, а не генерацию/свет/рандом-тики.
2. **Фейковый игрок** (`baseline_bot`, mineflayer, offline-режим, creative)
   — без игрока Paper EAR отправляет все мобы в `inactiveTick()` и бенчмарк
   был бы враньём. Бот стоит на спавне, энтити заполняются вокруг него
   (часть мобов — в радиусе активации 28 блоков, чтобы был честный AI-костёр,
   остальное — за пределами, как на реальных фермах).
3. **Plugin chunk tickets** (level 31 = entity ticking) на весь регион —
   иначе чанки без игрока не тикают энтити.
4. **Плавное заполнение** (батчи за N тиков) — чтобы не убить сервер на старте.
5. **Замер**: `ServerTickEndEvent.getTickDuration()` (мс/тик) на протяжении
   600 тиков после прогрева; перцентили p50/p90/p99/max; счётчики энтити
   каждые 100 тиков (видно усадку от merge); heap до/после.
6. **JFR** (`-XX:StartFlightRecording=settings=profile,dumponexit=true`) —
   из записи вытаскиваются top-фреймы по self-time → «что как нагружает»
   внутри JVM. Оверхед JFR ~2-5% — одинаковый для всех прогонов, влияет
   только на абсолют, не на сравнение.
7. Сервер сам пишет `baseline.json`, логирует `BASELINE-DONE` и гасится
   (`Bukkit.shutdown()`) — чтобы JFR корректно слился на выходе.

Состав предметов: 50% с pickupDelay=32767 (вечные, без merge),
50% сливаемые (реальный merge-скан). Усадка счётчика = работа merge.
Стойки (marker armor stands) — дешёвый тик-фLOOR на энтити.
Зомби: persistence + железный шлем (не сгорают), Paper `canMobPickup=false`.

## Что получим и как это используем

1. **Кривая MSPT от масштаба** — сколько стоит база и каждый класс нагрузки.
2. **Топ горячих методов** — ранжированный список целей оптимизации
   (подтверждение/опровержение гипотез §6 док-а 01).
3. **RAM-профиль** ванильной кучи на 100k+ — база для сравнения с Rust-зеркалом.
4. Контрольная точка для будущего A/B: тот же пайплайн + модуль CRUSSTY.

Никаких выводов об «оптимизации» до получения этих цифр не делаем.
